# Code of conduct

## The short version

Be decent to people. Argue with the code, not the person who wrote it.

This is a one-person project that deals with other people's private
conversations, so the bar for care is high and the tolerance for cruelty is
zero. That is the whole rule; the rest is detail for the cases where "be
decent" turns out to be ambiguous.

## What is expected

- **Criticise work, not people.** "This leaks the key on the error path" is
  useful. "Only an idiot would write this" is not, and it makes the first
  sentence easier to ignore.
- **Assume the other person knows something you don't.** Much of this codebase
  looks wrong until you read the comment three lines up explaining the
  hard-won reason it is that way.
- **Take "no" without a fight.** Not every feature belongs here. A maintainer
  declining something is not an invitation to relitigate it in five threads.
- **Respect people's privacy.** Do not post other people's messages, server
  addresses, screenshots containing someone's conversations, or anything from a
  deployment you do not run.

## What is not acceptable

Harassment, sexualised language or imagery, insults, personal or political
attacks, deliberate misgendering or deadnaming, publishing anyone's private
information, and sustained disruption of discussion. Trolling a security
report — or a person who filed one — counts.

None of this depends on whether you were joking.

## Scope

This applies in the issue tracker, pull requests, commit messages, code review
and any other space this project occupies, and it applies when you are
representing the project elsewhere.

## Reporting

Report privately rather than in a public thread. The only private channel this
repository has is GitHub's **Security → Report a vulnerability** form, which
opens a private advisory the maintainer can read; use it and say plainly that
it is a conduct report rather than a security one. If you would rather not use
that route, contact the maintainer through their GitHub profile.

Reports are read by the maintainer, who is also the person who would act on
them. That is an honest limitation of a one-person project rather than a
policy: if your report is *about* the maintainer, you have no neutral party to
escalate to here, and you should feel free to say so publicly instead.

## Enforcement

Depending on severity: a private word, a public correction, edited or removed
comments, or a block from the repository. Deliberate harm to users — publishing
someone's private data, sabotaging a security fix — goes straight to the last
one.
