# E2EE audit, 2026-10

> **Status: everything it found is fixed in 0.9.847,** the release this document
> is published with: F-1, F-2, F-3 and F-5 in the code, F-4, F-6 and F-7 in the
> documents they concern. Each finding names its commit. Sections 1 to 7 are the
> audit as written, with each status brought up to date; §8 is the review that
> landed the fixes, including one more path F-1 had missed.

Scope: does the code deliver what `README.md`, `docs/E2EE.md`,
`docs/E2EE_RECOVERY.md`, `docs/SECURITY_MODEL.md`, `docs/PRIVACY.md` and
`docs/REMOTE_CONTROL.md` promise? Read against the tree this document was
added in. Line numbers are from that tree and will drift; the symbol names
beside them will not.

Method: every claim was traced to the code that enforces it and read for the
guard three lines away, then for the other callers. Candidate findings were
re-read adversarially before being counted — the prior audits here over-stated
severity (CLAUDE.md: of 13 HIGH/CRITICAL findings, two survived a re-read), so
anything not demonstrable from the code as written is labelled **unverified**
rather than reported as fact. Documented, deliberately accepted limits
(trust-on-first-use, no per-message forward secrecy for channel history, an
offline-crackable SRP verifier, server-visible metadata, unbound personal-note
fields) are not findings unless the code is worse than the doc says.

The earlier audit write-ups (2026-07-24, 2026-08-10, 2026-08-20, 2026-09-05,
0.9.810) are not in this repository (`SECURITY.md`, *What is already known*);
their items survive as tags in code comments, tests and the security model, and
are re-checked from those in §3.

What ran: the backend suite against a throwaway Postgres (`TEST_DATABASE_URL`
set, so the ~40 database-backed tests ran rather than skipping themselves:
669 passed, 0 skipped), the crypto-touching vitest suites (363 cases before
this audit's additions), and the new tests below.

## 1. Summary

One real regression of a previously-fixed finding; two gaps between what the
docs promise and what the client does; one screen that did not say what the
client already knew; and a handful of documentation inaccuracies. All are fixed
in 0.9.847. The cryptographic core — key custody, SRP, channel-key distribution
and rotation, envelope binding, DM v4, the device-control handshake — held up
under a close read (§4).

- **F-1 (High, fixed).** "Require encryption for calls" blocked the
  *microphone* on engines without the WebRTC Encoded Transform API (the H-3
  fix) but not the **camera or the screen share**: turning either on mid-call
  published it as plain DTLS-SRTP while the panel said media was blocked.
  Fixed in `frontend/src/api/rtc/manager.ts` with the same guard the join
  path already had; four new tests go red without it. Review found a third
  path — the setting switched on mid-call — and the same commit closes it
  (§8). 0.9.847, 0c27f7dc.
- **F-2 (Medium, fixed).** The H-1 write-up says an operator who forges channel
  membership to obtain the group key now has to "put a stranger in the member
  list where you can see them". The client wraps the key for, and attributes
  wrappers against, `GET /channels/:id/member-keys` — an endpoint no screen
  renders — and never compares it with the member list people see. The forged
  member stays invisible. Fixed in 0.9.847 (aeff0691, 012b6e8c): the key is wrapped only for,
  and a first-contact wrapper trusted only from, ids in both lists; any other
  is refused, and the app names the channel.
- **F-3 (Low, fixed).** `docs/E2EE_RECOVERY.md` §8 says login sanity-checks
  the unwrapped seed's public key against the stored one. It does not, and the
  client no longer calls `PATCH /keys/public` at all. Fixed in 0.9.847
  (b67e2054): both places that adopt a seed compare its key with the published
  one and stop on a mismatch.
- **F-4 … F-7 (Low/Info).** A stolen bearer token reads the same crackable
  password-wrapped seed as a database dump (not in the threat table); the
  safety-number screen warns on a verified-key change but not on a pin
  conflict; most `file:line` anchors in the security model have drifted; three
  statements in `docs/E2EE.md` describe an older state of the code. All
  corrected in 0.9.847 in the documents themselves; F-5 turned out to be a gap
  in the screen, not only in its wording, and is fixed there (3951d0e1).

F-2 is the documented residual limit of H-1 — forged membership yields the
group key — with its documented mitigation, visibility, missing; not a new way
to the key. It reaches call media in SFU channels as well as messages (§8).

### F-1 — camera and screen share bypassed "Require encryption for calls"

**Adversary.** Whoever sees the media path: the server operator, a TURN relay,
anyone on the network with the DTLS keys (the signalling server can substitute
fingerprints when the frame layer is off — SECURITY_MODEL §4, "The gap").

**Who is affected.** Engines without `RTCRtpSender.createEncodedStreams`:
Safari, iOS, Firefox, and the macOS/Linux desktop shells (WKWebView,
WebKitGTK). Chromium-family clients (Windows WebView2, the Android WebView,
Chrome, Edge) are not. On the affected engines the setting is armed for a
fresh install, by the owner's server-wide policy, or by the user; the
migration deliberately does not arm it on an upgraded profile there
(`settingsStore.ts` `migrateRequireMediaE2ee`).

**Path.** `addLocalMediaToPeer` refuses to add tracks when
`requireMediaE2ee && !isMediaE2eeSupported()` (manager.ts 972-980) and
`ontrack` drops inbound tracks the same way (1426-1431). Those two guards are
what `frontend/src/tests/mediaE2eeEnforcement.test.ts` pins, and they cover the
tracks present when a peer is *built*. A camera turned on or a share started
mid-call reaches the peers through `publishCameraTrack`, `toggleVideo`,
`switchCamera` and `addScreenShareToPeers` → `addScreenShareTracks`, each of
which called `pc.addTrack(...)` and then `wireSender`, which returns without
attaching a transform when the API is absent. The track therefore went out
unencrypted. The UI did not stop it: `setCameraEnabled` and the share start in
`VoicePanel.tsx` carry no enforcement guard; the pre-join notice above Join
says media is blocked.

**Fix.** `publishBlockedByEnforcement()` in `manager.ts`, called at the top of
the four publish paths: publishes nothing and reports `local-unsupported` on
every peer, the same reason the join-time guard reports. The local camera
preview still works. 27 lines. Review found a third path, the setting switched
on mid-call, and the same commit rebuilds every connection when it changes on
such an engine (§8).

**Evidence.** With the fix stashed, `mediaE2eeEnforcementCamera.test.ts`
fails its four SECURITY cases (toggleVideo, publishCameraTrack, switchCamera,
addScreenShareToPeers each published a `video` track); with it, all seven pass,
including the two controls that fail if the guard refuses everyone or refuses
with enforcement off.

### F-2 — the "stranger in the member list" mitigation is not enforced

**Adversary.** A malicious server operator (the H-1 adversary).

**Path.** When a member mints an epoch, `mintEpoch` fetches
`/channels/:id/member-keys`, pins each served key, and wraps the group key for
every id in that list (channelKeys.ts 436-452). When a member reads a wrapped
key whose wrapper it has never seen, `attributeWrapper` step 5 trusts the
wrapper if, and only if, the same endpoint lists that id under the same key
(196-205). Both decisions rest on one endpoint, served by the adversary. The
member list a person sees is a different request —
`/servers/:id/members-with-roles`, polled every ten seconds
(`frontend/src/hooks/queries.ts`) — and the channel-key code never reads it,
nor does the UI ever render `member-keys`. An operator who lists an extra id
on `member-keys` only therefore receives the group key from every honest
minter and can distribute keys as that id, and nothing on screen changes. The
docs' claim that the attack now "requires putting a stranger in the member
list where you can see them" holds only if the operator chooses to serve both
endpoints consistently.

**What is still true.** The wrap set is at least bounded to *channel viewers*
by the server (`src/key_handlers.rs` `get_member_keys` 593-621) — but that is
the server's own filter, which this adversary controls. A member of the channel
cannot do this: `publish_channel_keys` requires the publisher's own identity
key (248-270).

**Fix (0.9.847, aeff0691, 012b6e8c).** The owner's decision (D-1): warn and refuse.
`mintEpoch` wraps the key only for ids that are in member-keys AND in the
server's member list the app shows (the sidebar's own query), and
`attributeWrapper` trusts a first-contact wrapper only if it is in both,
including on the pinned fallback when member-keys fails, so failing that
request is no way round it. An id listed on member-keys only is refused, and
`HiddenRecipientBanner` names the channel and its server. Which server a
channel belongs to comes from the client's own channel lists
(`frontend/src/api/channelDirectory.ts`), never from a key endpoint. The
stale-list case the decision had to weigh is handled rather than refused: a
member who joined a moment ago is in member-keys before a cached list has
them, so the list is read again past the cache before anyone is refused, and
if that read fails, nothing is minted and nobody is reported (§8); a
list that does not contain the reader (the endpoint answers `[]` when its own
query fails) mints nothing and alarms nobody. What it does not close: an
operator who lists the stranger in BOTH lists. The stranger is then in the
member list where you can see them, which is the documented residual, and
safety numbers are what close it.

### F-3 — no own-key check at login

**Path.** `restoreIdentityAfterLogin` unwraps the seed and calls
`setActiveIdentity` (auth.ts 640-647). It never fetches
`/users/<me>/public-key`, and `/keys/wrap` does not return the key. So when the
server serves *other people* a different identity key for this account, the
account's own devices cannot tell; the only symptom is that channel keys and
DMs wrapped to the served key fail to open here. Contacts who already pinned
the real key refuse the substitute (fail closed, as documented); new contacts
pin the substitute. The doc describes a check that does not exist. The server
side is sound: `update_public_key` is proof-gated and refuses to change an
established v3 key (`src/handlers.rs` 2068, 2084-2098), so the substitution
needs the operator, not a token.

**Fix (0.9.847, b67e2054).** The owner's decision (D-2): stop the restore and
warn, never silently adopt, and lock no existing user out with a false
mismatch. `restoreIdentityAfterLogin` and the banner's retry
(`retryIdentityRestore`, a second place that adopts a seed, which the finding
did not name) read `/users/<me>/public-key` and compare it byte for byte with
the seed's key. A different, well-formed key is not adopted — a seed an
earlier session cached is cleared too — and `IdentityBanner` says the key is
not the one this server publishes. Nothing published, a pre-X25519 value, a
wrong-length value or a lookup that fails is not a mismatch: the seed is
adopted, with a console warning. The check runs at sign-in and on that
retry; a device that stays signed in checks at its next sign-in.

### F-4 — what a stolen bearer token reads

`GET /keys/wrap` answers a bare bearer with the password-wrapped seed and its
salt (and the recovery-wrapped history key). That is exactly the offline
target the recovery design's threat table describes for a database thief
("crackable only as far as the password is weak"); a token thief gets it for
one account. The docs say a copied token is good for up to 30 days and that
sign-out-everywhere ends it; they do not say it also yields this blob. Nothing
to change in the code — login needs the blob with only a bearer — but the
threat table should list it.

**Corrected (0.9.847).** `docs/E2EE_RECOVERY.md` §7 and the token paragraph
of `docs/SECURITY_MODEL.md` §1 now say it.

### F-5 — the safety-number screen and a pin conflict

`SafetyNumberModal` computes the number from `getCachedPublicKey(userId)` (the
served key) and reports `getVerificationState(userId, served)`, which is
`changed` only against a key the user *verified*. After a substitution of a
peer the user has merely pinned, DMs refuse with "Verify their safety number
before messaging", and the screen that sentence points at shows the
substitute's number with no warning that it differs from the key this device
has been using. Comparing the number out of band still detects the swap —
the partner computes a different one — so the model holds; the screen could
say what `identityPinConflicts` already knows.

**Fixed (0.9.847, 3951d0e1).** It was a gap in the screen, not only in its
wording: the screen now says when the key it shows is not the one this device
pinned for that person, and the button says it trusts a new key.

### F-6, F-7 — documentation drift

`docs/SECURITY_MODEL.md` opens with "Every claim below carries a `file:line`
reference"; most no longer point at their claim (for example `src/ws.rs:50`
is a doc comment about presence, `src/auth.rs:157` a rowless-session note,
`sfuManager.ts:192` an options object). The claims themselves were re-found by
symbol and hold (§4). `docs/E2EE.md` still says channel-key wraps "stay v2 for
now" (they have been context-bound v3 since 0.9.0, with a v3 floor in the
reader), that the identity key is re-uploaded on every login (no caller), and
that rotation has a last-writer-wins race (the server serialises an epoch
under an advisory lock and answers a rival with 409).

**Corrected (0.9.847).** The security model's anchors now name the function
or constant that enforces each claim instead of a line number. The three
statements in `docs/E2EE.md` are corrected, with a fourth of the same kind: v2
accounts no longer migrate at sign-in, they are refused.

## 4. What held up

Each line is a claim from the docs and the code that enforces it.

### Channel keys and rotation

- **A wrapper is attributed before it is encrypted under** (E2EE.md threat
  model, H-1): `attributeWrapper`, `frontend/src/api/channelKeys.ts` 149-213.
  The first-contact step accepts only an id the server also lists under the
  same key on `member-keys` (see F-2 for what that does and does not buy); a
  bare pin is deliberately not enough, and `hasIdentityPin` is read-only
  (`keyVerification.ts` 133-147). Unverifiable current epochs are read but
  trigger a rotation before the next send (`channelKeys.ts` 291-298, 618-633).
- **Member keys are pinned before the group key is wrapped for them** (M6):
  `mintEpoch`, `channelKeys.ts` 436-447; a served key that conflicts with a
  pin or a verified compare is skipped, never wrapped for.
- **Rollback to a superseded epoch is refused** (C-01): the per-channel epoch
  floor (`channelKeys.ts` 347-403, 542-565), the 409 branch adopting only an
  attributed, at-or-above-floor key (475-510), and a rotation that cannot be
  minted after a membership change refusing to send under the old key
  (642-660).
- **Epoch squatting cannot pin the key in place** (C12): rotation targets
  `max(current, max_epoch) + 1` (`channelKeys.ts` 418-420) and the server
  serves `max_epoch` beside the caller's own epoch (`src/key_handlers.rs`
  479-484, 549-556).
- **Server-side publish rules**: epoch bounded to `MAX+1` under an advisory
  lock (`key_handlers.rs` 186-223); every row in a publish must carry the
  publisher's own identity key (230-270); a rival publisher of an existing
  epoch gets 409 (271-289); the client-claimed generation is clamped so it can
  never suppress a rotation (291-315); recipients are filtered to channel
  viewers (317-331), as is `member-keys` (593-621); all three key routes are
  VIEW-gated (127-140, 422-434, 566-578).
- **Rotation is triggered by every membership change**: `server_members`
  insert/delete bump the generation and delete the departed member's wrapped
  rows (`migrations/015_e2ee_key_rotation.sql`); a permission change bumps it
  too, before the broadcast (`perms_changed`, `src/ws.rs` 5351-5366). The SFU
  media key is derived from the channel key per epoch
  (`e2ee.ts` `deriveSfuMediaKey`), so a rotation re-keys live SFU media and the
  LiveKit server, which only mints join tokens (`src/sfu.rs`), never holds it.
- **Key wraps are context-bound** (E2EE.md, v3 wraps): AAD
  `puca/v3/wrap/<channel>/<epoch>/<recipient>` (`e2ee.ts` 759-823), and once a
  device has opened a v3 wrap for a channel, an unbound v2 wrap at or above
  that epoch is refused (`channelKeys.ts` 318-323).

### Message envelopes, DMs and attachments

- **v3 AAD is recomputed from the row's own metadata and there is no retry
  under another context**: `decryptChannelMessage` / `decryptDM`,
  `e2ee.ts` 846-859, 625-640; the AAD grammar is closed (344-386); a DM row
  whose sender is neither participant is a context mismatch (`dms.ts` 259-262);
  a `self` envelope outside the self conversation is refused (230-241).
- **An envelope of an unknown version is never rendered as plaintext**:
  `parseEnvelopeEx`, `e2ee.ts` 1424-1440; `isEncrypted` counts it as sealed
  (1452-1454), so `messageEncState` cannot call it `legacy`; the badge is
  rendered from that state (`Chat.tsx` `NotEncryptedBadge` 332, 6095), and a
  plaintext row newer than a sealed one is `unexpected`, not `legacy`
  (`markUnexpectedPlaintext`, `liveEncState`).
- **A sealed body cannot be replaced by an older envelope or by plaintext on
  edit**: `src/envelope_version.rs` (`edit_is_downgrade`), applied in
  `src/message_handlers.rs` 613 and `src/task_handlers.rs` 1004-1015; every
  client edit path sends `reads_up_to` (`servers.ts` 175, `tasks.ts`,
  `listContent.ts`, `listConflict.ts`).
- **DM v4**: the MAC is checked first, under the pairwise identity DH, before
  any wrap is touched (`e2ee.ts` 561-603); each wrap binds both public keys
  and the body AAD (481-501); a wrap addressed to us that does not open is
  `bad`, not `locked` (599-602). The key list the sender wraps to is the
  server's, the vouching the account's: every entry must verify under the
  signing key (`dmKeys.ts` `verifyDmKeyInfo` 333-354), that key is accepted
  for a peer only with an attestation under the pairwise identity secret
  computed from the *pinned* identity key (`signingKeyFor` 363-376), and for
  ourselves only if it equals the one derived from our own seed (367-369). The
  attestation can be written only by the conversation's own participant into
  their own column (`src/handlers.rs` `set_dm_sign_attestation` 1925-1939).
- **Every AES-GCM nonce is 12 random bytes per call**: `e2ee.ts` 274-281
  (all envelope, wrap and seed paths), `attachments.ts` 279 (a fresh per-file
  key, used once), `frontend/src/api/rtc/mediaCrypto.ts` 97 (per frame). Clips use a counter
  nonce under a per-session key with the index in the AAD
  (`frontend/src/api/clips/clipCrypto.ts`) and re-key rather than reuse on
  re-seal.
- **Attachments**: a per-file random key travels only inside the sealed
  message (`attachments.ts` 271-302); the server stores `nonce || ciphertext`
  it has no key for, so it cannot substitute a blob that opens.

### Key custody and SRP

- **Every key-custody write needs a fresh password proof bound to the
  session that spends it**: `require_password_proof`
  (`src/recovery_handlers.rs` 171-188) on `/keys/rewrap` and
  `/keys/migrate-v3` (237), `/keys/rewrap-pw` (308), `/keys/change-password`
  (378) and `PATCH /keys/public` (`src/handlers.rs` 2068); the proof is
  recorded only by `login_step_2` (`handlers.rs` 786-789, 817) and matched on
  the session start (`src/state.rs` 1629-1648). A password change bumps
  `token_version`, hangs up every socket and consumes the proof
  (`recovery_handlers.rs` 394-424).
- **The identity public key cannot be swapped on a v3 account, even with a
  proof** (`handlers.rs` 2084-2098) — which is what keeps the recovery
  proof-of-possession (bound to `users.public_key`,
  `recovery_handlers.rs` 597-626) satisfiable by nobody but the seed holder.
- **The account signing key is write-once for a bare bearer and replaceable
  only by a session that just proved the password**
  (`handlers.rs` 1728-1744, 1993; `src/device_handlers.rs` 1538); a session's
  DM key is write-once per session (`handlers.rs` 2009-2011).
- **SRP**: the `srp` 0.6 crate refuses `A ≡ 0 (mod N)` (`process_reply`) and
  compares `M1` with `ct_eq`; the client checks the server's `M2`
  (`frontend/src/api/auth.ts` 537-540); unknown names get synthesised material
  and the same modexp on both steps (`handlers.rs` 443-476, 608-647);
  per-username backoff (563-571); the Argon2id verifier upgrade is applied only
  after `M1` verified and only while `srp_version = 1` (727-768). (Note, not a
  finding: the crate's `M1 = H(A ‖ B ‖ K)` is not RFC 5054's `M1`; both sides
  agree and `K` already binds `A`, `B` and the verifier.)
- **Recovery reset**: the challenge is one-shot with a TTL (561-564), every
  failure is one uniform 401 after identical work (551-651), the HMAC is
  verified in constant time (639-645), the rewrite is scoped to the exact row
  whose key authorised it (597-607), `token_version` is bumped and live sockets
  closed (695, 718, 741), and rotating the code without re-wrapping the history
  key is refused (671-686). A cross-language known-answer test pins the
  DH/HKDF/HMAC construction against the client (781-812).
- **Pins survive sign-out** (`auth.ts` 1267) and only an out-of-band
  verification moves one (`keyVerification.ts` 110-117); a conflict refuses the
  material outright (155-166). A server cannot roll a v3 account back to the
  password-derived identity (`auth.ts` 629-635, `e2ee_key_version_*`).

### Live media

- **Per-frame AES-GCM with the clear codec header as AAD and a random IV**
  (`frontend/src/api/rtc/mediaCrypto.ts` 93-109); under enforcement an outgoing frame to a peer
  that is not yet encrypting is dropped, never sent clear (88-92, 168), and an
  incoming unmarked, too-short or unauthenticated frame is dropped, never
  decoded (119-124, 148-150, 192). The encrypt transform is attached when a
  track is added (`manager.ts` `wireSender`), the decrypt transform in
  `ontrack` (1414-1417), both before any frame can flow; a stripped capability
  line leaves `enabled` false, which under enforcement is no media
  (321-343). `setRequireMediaE2ee` reaches peers already connected (270-277)
  — where the transforms exist; on the engines without them it did not (§8).
- **The DTLS fingerprint is pinned under the pairwise static key on every
  engine** (`frontend/src/api/rtc/mediaCrypto.ts` 244-285), the mismatch is latched for the
  peer's life (`manager.ts` 222-240) and outranks every other reason in the
  badge (259-263).
- **The SFU path fails closed**: no Encoded Transform means no join
  (`frontend/src/api/rtc/sfuManager.ts` 596-598), no channel key means no join (600-604), and a
  remote publication flagged unencrypted is never rendered (1735-1737); the
  server-wide "require" flag is written by the owner only
  (`src/server_handlers.rs` 769-771).

### Remote control

- **A controller's key comes only from an enrolment record that verified under
  the account signing key this client derived from its own seed**
  (`frontend/src/api/devices/peerKeys.ts` 70-82; `identityRc.ts`
  `verifyAuthRecordWithKey` 23-46 also binds the record's device id, user id and
  both keys and re-canonicalises). A friend's device is accepted only after the
  host re-verifies its *own* grant signature over exactly the share's
  capabilities (`shares.ts` `shareAuthorises` 128-155) and the friend's device
  record under the friend's pinned signing key (`verifiedSharePeerDevice`
  246-264), in that order, in the connect handler (`session.ts` 4053-4129).
- **Signalling is sealed with no unsealed fallback**: `sendSignal` returns
  without a key (`session.ts` 1039-1071), frames are bound to the session id
  and strictly ordered (1074-1084); the server relays `DeviceSignal` to the
  one target connection and gates `DeviceInput` on the controller connection,
  the active state and `allow_input` (`src/ws.rs` 4451-4495).
- **Input needs the share's `control` capability, the unattended proof when
  armed, a capture-capable host, and a strictly increasing sequence under the
  session key** (`session.ts` 4579-4618); the armed state is read from the
  native side (`unattendedHost.ts` `unattendedState`), never from the server;
  the passphrase record is an Ed25519 verifying key plus salt with a lockout
  after `FREE_FAILURES` (`crates/puca-ua/src/lib.rs` 63-91, 227-238).
- **In-call screen-share control** derives its key from the *pinned* peer
  identity plus fresh ephemerals (`remoteControl.ts` 205-243), grants only
  from the Allow handler or a host-initiated offer (1150, 1272), seals every
  event with a per-session sequence (885-886, 1457-1458) and injects only while
  actively sharing (484-487).
- **The agent's pipe is owner-and-SYSTEM only with a per-launch token**
  (`crates/puca-agent/src/pipe.rs` 31-56; `protocol.rs` `Hello { token }`),
  and the service's protocol has a test that an injection attempt is refused
  (`crates/puca-service/src/control_pipe.rs`
  `an_injection_attempt_is_refused_and_not_echoed`). The desktop shell's
  capability file grants no remote origin IPC
  (`frontend/src-tauri/capabilities/default.json`).

## 5. Unverified

Things this audit could not confirm either way, and what would.

- **LiveKit's behaviour towards a participant that cannot decrypt.** The
  client refuses to render an unencrypted publication and derives the key from
  the channel key, so such a participant cannot read anyone; whether LiveKit
  would still *forward* encrypted frames to it was not exercised (needs a
  LiveKit deployment; `frontend/e2e/games-live.mjs`-style harness).
- **Transform attachment versus the first frame, in a real engine.** The
  ordering is right by construction (transform at `addTrack`, decrypt at
  `ontrack`), not measured; a real-browser script in the style of
  `frontend/e2e/ice-url-real-browser.mjs` could capture the first frames.
  (Measured since, §8: what the publish paths put on the wire on an engine
  without the API, in real Firefox, and that a reused sender still takes the
  transform in real Chromium and Edge. The first-frame ordering itself is
  still unmeasured.)
- **Media frame reflection and replay.** Mesh frames carry no direction or
  sequence binding (one pairwise key both ways, random IV, AAD = codec header),
  so a relaying server could reflect a peer's frames back or replay frames
  within a session. Not a confidentiality break and no doc claims replay
  protection for media; whether a decoder would accept such frames was not
  tested.
- **The native remote-control layer** (`crates/puca-agent/src/session.rs`,
  `crates/puca-service/src/link.rs`) was checked for its pipe ACL, token and
  the injection-refusal test only; its Windows-only paths cannot run here.
- **Anything in §4 cited by line that was read but not executed.** The
  backend and vitest suites named above ran; the e2e harnesses that need a
  backend, a LiveKit or a display did not.

## 6. Decisions (made by the owner, 2026-10-23)

Written up rather than made, because each changes behaviour or a documented
promise. Each is now decided, and the decision is the first line of its item.
Publication was decided too: this document ships in the same release as the
fixes, so nothing it describes is still open when people read it.

- **D-1 (F-2). Make the forged-member attack visible, or stop claiming it is.**
  **Decided: warn and refuse** — option (a), with a notice naming the channel.
  Implemented (aeff0691, 012b6e8c).
  Options: (a) have the channel-key code restrict the wrap set and the
  first-contact attribution to ids present in the member list the client has
  rendered — same adversary serves both, so it buys visibility only, and a
  send would have to fail (or wait) while that list is unloaded; (b) render
  the wrap set itself — "encrypted for N members", listing the ids the key
  was wrapped for, derived from `member-keys`, so a stranger has somewhere to
  be seen; (c) leave the code and reword `docs/E2EE.md` and
  `docs/SECURITY_MODEL.md` §3 to say the forged member is *not* visible today.
  (b) plus the doc fix is the smallest change that makes the claim true.
- **D-2 (F-3). Decided: stop the restore and warn** (b67e2054). The question was:
  what a device does when the server serves a different identity
  key for its own account.** The check is one request after the unwrap
  (`/users/<me>/public-key` against `makeIdentity(seed).publicKeyEncoded`).
  The decision is the response: refuse the session, or sign in and raise a
  banner that refuses sends until the operator fixes it (the
  `identityRestoreFailed` machinery is the natural home). Either needs UI,
  which is why it is not done here.
- **D-3 (F-4 … F-7). Decided: correct them in the same release.** Done, with
  F-5 fixed in the screen (3951d0e1). The items were: Add token theft to the recovery threat
  table; have the safety-number screen surface `identityPinConflicts`; replace
  the drifted `file:line` anchors in the security model with symbol names (or
  a script that checks them, as `scripts/check-docs-links.mjs` checks paths);
  correct the three stale statements in `docs/E2EE.md` and the login
  sanity-check sentence in `docs/E2EE_RECOVERY.md`.

## 8. Review addendum (2026-10-23)

A second read before F-1 landed, with a sweep of every path that can put
media on the wire. F-1 landed with the extension below; F-2, F-3 and F-5
were fixed after it in the same release, on the owner's decisions (§6).

- **F-1 had a third way round the setting, fixed with it.** On an engine
  without Encoded Transform, `setRequireMediaE2ee` only flipped a flag that
  nothing reads there (there is no transform to read it). So the setting
  switched on *during* a call — the member's own, or the server's policy
  arriving — left the mic, camera and share already on the connections going
  out in the clear, and every inbound track playing, while the panel switched
  to "media is blocked both ways". The §4 line "`setRequireMediaE2ee` reaches
  peers already connected" holds only where the transforms exist. Fixed in the
  same change: on such an engine `setRequireMediaE2ee` now rebuilds every peer
  through the join-time guards. Closing a connection stops both directions at
  once, and switched off, the rebuild brings the media back without a rejoin.
  `frontend/src/tests/mediaE2eeEnforcementToggle.test.ts`: two SECURITY cases
  and three controls; both SECURITY cases, and the turned-off control, go red
  without the rebuild.
- **Measured in a real engine.** Two Firefox 155 pages (no
  `createEncodedStreams`, so `isMediaE2eeSupported()` is false), each running
  the real `manager.ts`, signalling relayed by the harness, bytes read from the
  engine's own stats. Pre-fix trunk: a camera and a share started under
  enforcement put 111 KB of video on the wire in 6 s, and enforcement switched
  on mid-call left 24 KB of audio and 103 KB of video flowing in the next 3 s.
  With the fix: 0 bytes in both, and switching it off restored the mic through
  a rebuilt connection. The controls (enforcement off) published and received
  video, so the rig could see a publish. The harness is not a gate yet.
- **A test that could not fail.** F-1's "the refusal is reported as
  local-unsupported" case passed without the guard, because `mediaE2eeStatus`
  derives that reason from the engine alone. It now asserts the status
  announcement that only the guard makes.
- **Swept and sound, no change.**
  - The SFU publish path: the room exists only after LiveKit's
    `isE2EESupported()` (Encoded Transform or `RTCRtpScriptTransform`), and
    every `publishTrack` gets LiveKit's encryptor on `LocalSenderCreated`,
    before negotiation. That covers the mic, the republished mic, the camera,
    the camera flip, and the share's video and audio.
  - Screen-share audio: published with the share, behind the same guard. A
    live change of audio sources re-mixes the one native track.
  - Rebuild paths: renegotiation, ICE restart, rebuild, rejoin, Move here and
    NO_RECEIVE re-admission all build the peer again through
    `addLocalMediaToPeer`.
  - The noise-mode and device-watchdog mic swap (`doReapplyNoiseMode`): its add
    branch already had the guard. Its replace branch can only find a sender
    that was published before enforcement went on, and the rebuild now removes
    those.
  - Pop-out windows render the same MediaStream over no new connection.
  - The Android WebView and Windows WebView2 are Chromium, so the transforms
    exist there.
  - The Lite build runs the same manager; only the control lane differs.
  - In real Chromium 153 and Edge 155, a sender that `addTrack` reuses from an
    earlier transceiver (an answerer's camera, a listen-only join's mic) still
    takes `createEncodedStreams()`, so the paths that reuse one are encrypted
    too.
- **Out of the setting's reach, by design.** My Devices sessions are not calls:
  they are DTLS-SRTP under signalling sealed with the device key. Peer-to-peer
  file transfer uses data channels, not media.
- **F-2 reaches calls too.** The SFU media key is derived from the channel key
  (`deriveSfuMediaKey`). An id the server lists on `member-keys` only therefore
  also gets what it needs to decrypt that channel's SFU calls, which the
  server's own SFU forwards. Mesh calls are not affected: they use pairwise
  identity keys.
- **F-2's first version could raise a false alarm, fixed in the same
  release.** When the cached member list lacked an id that member-keys named,
  the list was read again past the cache, as it should be. But if that read
  failed, the cached list was kept, so a member who had joined a moment ago
  was reported as not a member and left out of the epoch being minted. A
  failed second read now establishes nothing: no epoch is minted, no
  first-contact wrapper is trusted, nobody is reported, and the send is
  refused as "try again in a moment" (012b6e8c). Two controls in
  `channelKeysWrapSetVisibility.test.ts`, one for a mint and one for a wrapper
  on load, go red against the first version.
- **Left as a decision.** The camera and share starts in `VoicePanel.tsx` still
  announce (CameraStarted, ScreenShareStarted) before the manager refuses the
  publish, so the others see a camera or a LIVE share that never arrives. No
  media leaves. Refusing at the button, with the panel's explanation, would be
  the better behaviour.
