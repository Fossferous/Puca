## 4. What held up

Each line is a claim from the docs and the code that enforces it.

### Channel keys and rotation

- **A wrapper is attributed before it is encrypted under** (E2EE.md threat
  model, H-1): `attributeWrapper`, `frontend/src/api/channelKeys.ts:149-213`.
  The first-contact step (5) accepts only an id the server also lists under
  the same key on `/channels/:id/member-keys`; a bare pin is deliberately not
  enough, and `hasIdentityPin` is read-only (`keyVerification.ts:133-147`).
  Unverifiable current epochs are read but trigger a rotation before the next
  send (`channelKeys.ts:291-298, 618-633`).
- **Member keys are pinned before the group key is wrapped for them** (M6):
  `mintEpoch`, `channelKeys.ts:436-447`; a served key that conflicts with a
  pin or a verified compare is skipped, never wrapped for.
- **Rollback to a superseded epoch is refused** (C-01): the per-channel epoch
  floor (`channelKeys.ts:347-403, 542-565`), the 409 branch adopting only an
  attributed, at-or-above-floor key (`475-510`), and a rotation that cannot be
  minted after a membership change refusing to send under the old key
  (`642-660`).
- **Epoch squatting cannot pin the key in place** (C12): rotation targets
  `max(current, max_epoch) + 1` (`channelKeys.ts:418-420`) and the server
  serves `max_epoch` beside the caller's own epoch (`src/key_handlers.rs:479-484, 549-556`).
- **Server-side publish rules**: epoch bounded to `MAX+1` under an advisory
  lock (`key_handlers.rs:186-223`); every row in a publish must carry the
  publisher's own identity key (`230-270`); a rival publisher of an existing
  epoch gets 409 (`271-289`); the client-claimed generation is clamped so it
  can never suppress a rotation (`291-315`); recipients are filtered to channel
  viewers (`317-331`), as is `/member-keys` (`593-621`); all three key routes
  are VIEW-gated (`127-140, 422-434, 566-578`).
- **Rotation is triggered by every membership change**: `server_members`
  insert/delete bump the generation and delete the departed member's wrapped
  rows (`migrations/015_e2ee_key_rotation.sql`); a permission change bumps it
  too, before the broadcast (`perms_changed`, `src/ws.rs:5351-5366`).
- **Key wraps are context-bound** (E2EE.md, v3 wraps): AAD
  `puca/v3/wrap/<channel>/<epoch>/<recipient>` (`e2ee.ts:759-823`), and once a
  device has opened a v3 wrap for a channel, an unbound v2 wrap at or above
  that epoch is refused (`channelKeys.ts:318-323`).

### Message envelopes

- **v3 AAD is recomputed from the row's own metadata and there is no retry
  under another context**: `decryptChannelMessage` / `decryptDM`,
  `e2ee.ts:846-859, 625-640`; the AAD grammar is closed
  (`e2ee.ts:344-386`).
- **An envelope of an unknown version is never rendered as plaintext**:
  `parseEnvelopeEx`, `e2ee.ts:1424-1440`; `isEncrypted` counts it as sealed
  (`1452-1454`), so `messageEncState` cannot call it `legacy`.
- **A sealed body cannot be replaced by an older envelope or by plaintext
  on edit**: `src/envelope_version.rs` (`edit_is_downgrade`), with the
  reader-first `reads_up_to` exception the doc describes.
- **DM v4**: the MAC is checked first, under the pairwise identity DH, before
  any wrap is touched (`e2ee.ts:561-603`); each wrap binds both public keys
  and the body AAD (`481-501`); a wrap addressed to us that does not open is
  `bad`, not `locked` (`599-602`).
- **Every AES-GCM nonce is 12 random bytes per call**: `e2ee.ts:274-281`
  (all envelope, wrap and seed paths), `attachments.ts:279` (per-file key,
  used once), `rtc/mediaCrypto.ts:97` (per frame). Clips use a counter
  nonce under a per-session key with the index in the AAD
  (`clips/clipCrypto.ts`), and re-key rather than reuse on re-seal
  (`clipTypes.ts:67`).

### Key custody and SRP

- **Every key-custody write needs a fresh password proof bound to the
  session that spends it**: `require_password_proof`
  (`src/recovery_handlers.rs:171-188`) on `/keys/rewrap` and
  `/keys/migrate-v3` (`237`), `/keys/rewrap-pw` (`308`),
  `/keys/change-password` (`378`) and `PATCH /keys/public`
  (`src/handlers.rs:2068`); the proof is recorded only by `login_step_2`
  (`handlers.rs:786-789, 817`) and matched on the session start
  (`src/state.rs:1629-1648`). A password change bumps `token_version`, hangs up
  every socket and consumes the proof (`recovery_handlers.rs:394-424`).
- **The identity public key cannot be swapped on a v3 account, even with a
  proof** (`handlers.rs:2084-2098`) — which is what keeps the recovery
  proof-of-possession (bound to `users.public_key`,
  `recovery_handlers.rs:597-626`) from being satisfiable by anyone but the
  seed holder.
- **The account signing key is write-once for a bare bearer and replaceable
  only by a session that just proved the password**
  (`handlers.rs:1728-1744`, `1993`; `src/device_handlers.rs:1538`); a
  session's DM key is write-once per session (`handlers.rs:2009-2011`).
- **SRP**: the `srp` 0.6 crate refuses `A ≡ 0 (mod N)`
  (`process_reply`) and compares `M1` with `ct_eq`; the client checks the
  server's `M2` (`frontend/src/api/auth.ts:537-540`); unknown names get
  synthesised material and the same modexp on both steps
  (`handlers.rs:443-476, 608-647`); per-username backoff (`563-571`); the
  Argon2id verifier upgrade is applied only after `M1` verified and only
  while `srp_version = 1` (`727-768`).
- **Recovery reset**: the challenge is one-shot with a TTL (`561-564`),
  every failure is one uniform 401 after identical work (`551-651`), the HMAC
  is verified in constant time (`639-645`), the rewrite is scoped to the exact
  row whose key authorised it (`597-607`), `token_version` is bumped and live
  sockets closed (`695, 718, 741`), and rotating the code without re-wrapping
  the history key is refused (`671-686`). A cross-language known-answer test
  pins the DH/HKDF/HMAC construction against the client (`781-812`).
- **Pins survive sign-out** (`auth.ts:1267`) and only an out-of-band
  verification moves one (`keyVerification.ts:110-117`); a conflict refuses
  the material outright (`155-166`).

### Live media

- **Per-frame AES-GCM with the clear codec header as AAD and a random IV**
  (`rtc/mediaCrypto.ts:93-109`); under enforcement an outgoing frame to a peer
  that is not yet encrypting is dropped, never sent clear (`88-92, 168`), and
  an incoming unmarked, too-short or unauthenticated frame is dropped, never
  decoded (`119-124, 148-150, 192`).
- **The DTLS fingerprint is pinned under the pairwise static key on every
  engine** (`rtc/mediaCrypto.ts:244-285`), independent of frame encryption.
